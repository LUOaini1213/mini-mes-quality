# mini-mes-quality

A small, end-to-end **manufacturing quality** demo: an MES-style data model with lot genealogy, unsupervised visual
defect detection on a public industrial image dataset, defect -> lot -> equipment/material traceability with proper
statistics, and a grounded SOP question-answering assistant.

> **Personal portfolio project, October 2026, built with AI assistance (Claude).**
> All MES data, all SOP documents and the image-to-unit mapping are **synthetic**. The images are real public
> benchmark images (VisA, CC BY 4.0) and are not stored here. This is **not** a real factory, a real MES or a
> deployed system, and it is not based on any company's data or documents.

Main limits: the MES data, its root causes and the SOP documents are synthetic; about 400 real test images are
reused round-robin across roughly ten thousand synthetic units per seed; the SOP test set has 32 questions; the
hybrid SOP row needs a locally downloaded embedding model, and the vision rows need the VisA images and a GPU-sized
run (CI recomputes the MES and BM25-only SOP results, see "Tests").

## What is real and what is synthetic

| Part | Real | Synthetic |
|---|---|---|
| Visual inspection | VisA `pcb1` / `pcb4` images, official one-class split, official masks; ImageNet-pretrained torchvision weights | - |
| MES data | - | everything: work orders, lots, split/merge genealogy, equipment, pseudonymous operators (`OP-###`), material batches, timestamps, injected root causes |
| Vision -> MES link | detector scores and decisions on real test images | which image a synthetic unit "gets" (matched to the unit's synthetic true state) |
| SOP assistant | retrieval / refusal code, evaluation | the nine SOP documents and the question set |

## How it works

### 1. MES data model (`mesq/schema.sql`, `mesq/schema_postgres.sql`, `mesq/generator.py`, `mesq/db.py`)

Tables: `product`, `route_step`, `equipment`, `operator`, `material_batch`, `work_order`, `lot`, `lot_genealogy`
(SPLIT / MERGE edges with quantities), `lot_step` (track-in / track-out per step with equipment, operator, shift),
`material_consumption`, `unit`, `unit_lot` (every lot a unit has been in), `inspection_result`, plus `gt_unit` /
`gt_cause` holding the generator's ground truth (only the scorer reads them). The SQLite file uses the same SQL as
DuckDB; `schema_postgres.sql` is the Postgres DDL (a test keeps both in sync).

The synthetic line builds a PCB assembly through PRINT -> PLACE -> REFLOW -> AOI -> ASSY. Lots are split after
PLACE and merged back after AOI, so **a unit's REFLOW/AOI history lives on a child lot, not on its final lot** -
traceability must go through the genealogy (`db.unit_history`, `db.where_used`, recursive CTEs `ancestors` /
`descendants`). One mutation in the mutation test replaces the genealogy join with "final lot only", and the tests
catch it.

Injected ground truth (documented in `mesq/generator.py`):

* **Drift**: `PNP-02` on night shift `C`, from day 10, ramping up to +22 points of defect probability.
* **Bad batch**: solder paste `SP-B07`, +12 points.
* **Traps** (no causal effect, but correlated with a cause): operator `OP-009` mostly runs `PNP-02` at night;
  oven `RFL-02` is "down for maintenance" while `SP-B07` is loaded, so those lots go to `RFL-01`.

### 2. Visual inspection (`mesq/vision/`)

* **PatchCore-lite**: WideResNet-50-2 (torchvision ImageNet weights) layer2+layer3 features, 3x3 local averaging,
  1024-d, greedy k-center coreset (10%) of patches from 400 normal training images, nearest-neighbour distance as
  the patch score; image score = max patch score; maps upsampled and Gaussian-smoothed. Images resized to 256x256
  (no centre crop).
* **Simpler baselines**: `global_knn` (global-pooled features of the same backbone, 5-NN distance; image score
  only) and `pixel_zscore` (per-pixel z-score against the normal training images; no learning).
* **Metrics** on the official VisA one-class test split: image AUROC, pixel AUROC, AUPRO up to FPR 0.3 (per-region
  overlap, as defined for MVTec AD). The FAIL/PASS threshold is the 95th percentile of scores on 100 held-out
  *normal training* images - fixed before looking at the test set.
* Memory-light for a 4 GB GTX 1650 (batch 4, fp16 feature storage, chunked kNN); runs on CPU too, slowly.

### 3. Vision -> MES -> root cause (`mesq/link.py`, `mesq/trace.py`, `mesq/stats.py`)

Each synthetic unit is given a real VisA test image whose label equals the unit's synthetic true state (defective
units get anomalous images); the PatchCore-lite decision on that image becomes the unit's AOI result, so real
detector misses and false alarms flow into the analysis. The pool has 401 test images for roughly ten thousand
units per seed, so images are reused round-robin; the `no_reuse` mode shows what happens with only as many units as
the pool covers without reuse.

The analysis never reads ground truth:

1. **Naive screen** - for every equipment, operator, shift, equipment x shift and material batch level at or before
   AOI: one-sided Fisher exact test, risk ratio with Katz CI, Wilson CI on the rate, Benjamini-Hochberg across all
   candidates.
2. **Explain-away selection** - forward selection by Cochran-Mantel-Haenszel tests stratified by calendar week and
   by the causes already selected (Bonferroni over the remaining candidates), then backward elimination.

It is scored against the injected causes over 20 generator seeds, for perfect inspection (`oracle`), the real
detector (`detector`) and the no-reuse subset. False leads are reported, both at the naive-screen stage and after
selection.

### 4. SOP assistant (`mesq/sop.py`, `mesq/sop_eval.py`, `sop/`)

Nine synthetic SOPs (printing, placement, reflow, AOI, lot handling, nonconformance, battery module assembly,
maintenance, ESD). Hybrid retrieval: BM25 + `BAAI/bge-small-en-v1.5` embeddings (loaded offline from the local
Hugging Face cache; download it once, see "Reproduce") fused with reciprocal-rank fusion; BM25-only when the model
is absent (CI). Answers are
**extractive**: the single best numbered SOP clause, verbatim, with a citation like `[SOP-AOI-004 section 4]`.
The assistant refuses when the best dense similarity is below a threshold or too many question terms are unknown to
the corpus; both thresholds are chosen on the 10 dev questions only. The 32 test questions (8 unanswerable,
several deliberately near-miss) are hash-frozen (`sop/questions.sha256`; a test fails if the file changes) and
were scored once. That they were written before the retrieval code is the author's own record: the public history
is a single commit, so git cannot show the order. Answers are extractive by design; no LLM is used. BM25/RRF code is adapted
from the author's earlier `fm-knowledge-assistant` project.

### Where the analysis goes wrong (from `results/mes/trace_runs.csv`)

* **Naive screening is full of false leads.** With perfect inspection, many more factors pass the BH screen than
  with the real detector - not because the detector helps, but because perfect labels give every confounded factor
  (night-shift operators, batches in use while the machine drifted) enough power to look significant. Stratification
  removes nearly all of them.
* **The planted operator trap wins once.** In seed 16 (oracle mode) the stratified selection picks operator
  `OP-009` instead of `PNP-02 x night shift`: in that seed the operator explains the drift slightly better than the
  machine does. An analyst would need equipment logs (offset trends, see SOP-MNT-008) to break the tie.
* **Small bad batches are missed with the real detector.** When `SP-B07` reached only a few lots, the detector's
  false-alarm rate (about one in ten good boards) drowns the signal (seeds 3, 6, 13).
* **The real detector also produces false leads.** In two seeds the detector-mode selection keeps an operator
  that is not an injected cause (`OP-012`, at REFLOW in one seed and at PRINT in the other); in one of them the
  drift cause is missed as well. The generated per-seed list under the traceability table names every miss and
  false lead for each mode.
* **Without image reuse there is no analysis.** The `no_reuse` subset (about 200 units, a handful defective)
  recovers nothing - a few hundred inspected boards are not enough for lot-level root-cause statistics at a 3%
  defect rate.
* **The vision threshold drifts.** The FAIL threshold was set for 5% false alarms on held-out normal *training*
  images, but gives about 11% on the normal *test* images of both categories.

## Comparison with published results (vision)

Published PatchCore numbers for these categories (He et al. 2024, MambaAD, arXiv:2404.06564, Tables A15/A16,
single-class VisA, 256x256) and PaDiM numbers from the VisA paper (Zou et al., ECCV 2022, Tables 7/8) are listed
under the results table. Differences to expect: this implementation keeps only 400 of the 904 training images in
the memory bank, uses no image-score re-weighting, and runs a single seed; published numbers also vary between
reproductions. The published values are the method family's reference, not a target that anything was tuned for.

## Tests

`python -m pytest -q` covers genealogy queries (hand-built split/merge fixture: ancestors, descendants, forward
"where-used" and backward unit history), generator invariants (determinism, pseudonymous IDs, injected effects
present, bad-batch exposure on every results seed, ground truth recoverable with perfect inspection), statistics
against hand-computed values (Wilson, Katz, BH, Holm, CMH), metrics against scikit-learn and constructed cases
(AUROC with ties, AUPRO region weighting), coreset/kNN logic on synthetic arrays, the image-to-unit mapping, SOP
retrieval/citation/refusal and the frozen question set, and the README numbers. CI runs them on synthetic fixtures
plus the committed `results/` (no images, no embedding model), on Ubuntu and Windows.

`tests/test_results_regenerate.py` goes one step further for the results that are cheap to recompute: it reruns the
20-seed traceability experiment from the committed per-image scores (`results/vision/*_scores.csv`) and the
BM25-only SOP evaluation, and checks that they equal `results/mes/trace_summary.json` and the `bm25_only` entry of
`results/sop/sop_eval.json` (about a minute). The vision metrics (they need the VisA images) and the hybrid SOP row
(it needs the embedding model) are not recomputed in CI.

The tests were themselves checked by breaking the code on purpose (`tools/mutation_test.py`). The first run caught
24 of 26 mutations; the two survivors (dropping the multiplicity correction in the forward-selection step, and
accepting an answer when any instead of all answer keys match) led to two new assertions, and the second run catches
all of them (see the generated block above).

## Honest limitations

* The MES and its root causes are synthetic, so recovering them shows that the *analysis pipeline* works on data
  with a known answer - not that it would find causes in a real plant.
* Image reuse makes the detector-mode sample larger than the number of distinct images; per-unit errors are real
  detector errors, but they are not independent across reused images.
* The SOP test set is small (32 questions) and the documents are short and clean; refusal thresholds chosen on 10
  dev questions do not transfer perfectly (see the test results). Extractive answers are verbatim by construction,
  which guarantees support but not that the best clause was picked.
* MVTec AD was not used (registration form; see DATA_SOURCES.md).

## Reproduce

Python 3.11 (CI uses 3.11 on Ubuntu and Windows).

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
# CUDA build as used for results/vision; for CPU only use --index-url https://download.pytorch.org/whl/cpu
pip install torch==2.5.1 torchvision==0.20.1 --index-url https://download.pytorch.org/whl/cu121
pip install -r requirements.txt
# one-time download of the SOP embedding model (about 130 MB) into the Hugging Face cache;
# run_all.py itself runs offline and stops before writing anything if the model is missing
python -c "from sentence_transformers import SentenceTransformer; SentenceTransformer('BAAI/bge-small-en-v1.5')"
# VisA: download the archive listed in DATA_SOURCES.md and extract pcb1, pcb4, split_csv to data/visa/raw
#       inside this repository (git-ignored), or set MESQ_VISA_ROOT to another folder
python run_all.py                  # everything; --reuse-vision skips recomputing the CNN part,
                                   # --bm25-only runs without the embedding model and drops the hybrid row
python -m pytest -q                # tests (CI runs these on synthetic fixtures + committed results)
python tools/mutation_test.py      # hand-written mutation test of the test suite
```

Outputs: `results/vision/` (metrics, per-image scores), `results/mes/` (screens, weekly rates, 20-seed summary),
`results/sop/` (answers, metrics), `results/headline.json`, `results/report.html`, `results/mutation.json`. The
SQLite MES databases are written to `build/` (ignored by git).

## 中文简介

个人作品集项目（2026 年 10 月，借助 AI 辅助完成）。演示制造业质量数据与 AI 的完整链路：

1. **MES 数据模型**：工单、批次、工艺路线、设备、操作员（只用假名编号）、物料批次、检验结果，以及批次拆分/合并谱系；
   SQLite 实现并附 Postgres DDL。数据全部由带随机种子的生成器**合成**，注入已知根因（夜班某贴片机漂移、某批锡膏不良）
   和两个“陷阱”混杂因素，用来给追溯分析打分。
2. **视觉检测**：在公开数据集 VisA（CC BY 4.0，PCB 类别 pcb1/pcb4，官方测试划分）上实现 PatchCore-lite 和两个更简单的
   基线，报告图像级 AUROC、像素级 AUROC 与 AUPRO，并与论文公开数值对比。MVTec AD 需要先填登记表才能下载，且为非商用
   （CC BY-NC-SA）许可，因此改用可直接下载、CC BY 4.0 的 VisA。
3. **缺陷→批次→设备追溯**：把真实图像的检测结果挂到合成单元上，用 Fisher 精确检验 + BH 校正初筛，再用按周和已选因素
   分层的 CMH 检验做“解释消除”，在 20 个种子上评估能否找回注入的根因，并如实报告误报线索。
4. **SOP 知识助手**：9 份**合成** SOP，BM25 + 本地向量模型混合检索，逐条原文引用作答，文档未覆盖时拒答；测试题已用哈希冻结
   （文件一改测试就失败；“先于检索代码写成”是作者自己的记录，公开历史只有一次提交，无法从 git 核验），阈值只在开发集上选。
